# Отчёт по лабораторной работе: GitHub Actions

## Контрольные вопросы

### 1. Из каких элементов состоит workflow и как они вложены друг в друга?

Workflow — это YAML-файл в каталоге `.github/workflows/`. Он состоит из названия (`name`), события-триггера (`on`) и набора заданий (`jobs`). Каждый job содержит runner (`runs-on`) и список шагов (`steps`). Каждый step — это либо shell-команда (`run`), либо вызов готового action (`uses`).

Вложенность: **workflow → jobs → steps**.

### 2. Чем job отличается от step?

Job — это набор шагов, который выполняется на одной виртуальной машине (runner). Разные jobs по умолчанию идут параллельно, у каждого своя чистая машина, и файлы между ними сами не передаются. Step — одна команда или один action внутри job. Шаги выполняются по порядку и на одной машине, поэтому видят общие файлы.

### 3. Чем запуск по push отличается от запуска кнопкой (workflow_dispatch)?

`push` срабатывает автоматически при каждой отправке коммитов в репозиторий. `workflow_dispatch` запускается вручную: кнопкой Run workflow на вкладке Actions (или командой `gh workflow run`). Ручной запуск удобен для задач, которые нужны по требованию, и может принимать входные параметры (`inputs`).

### 4. Как безопасно передать в workflow пароль или токен?

Через секреты репозитория (Settings → Secrets and variables → Actions) и обращение `${{ secrets.ИМЯ }}`. В логах значение секрета заменяется на `***`, что я проверила на практике (секрет `MY_SECRET`). Нельзя записывать пароли и токены прямо в YAML-файл или в код: они попадут в историю репозитория.

### 5. Что такое артефакт и зачем он нужен?

Артефакт — это файл (или набор файлов), сохранённый по итогам запуска через `actions/upload-artifact`. Он нужен, чтобы:
- передавать файлы между jobs (у них разные машины и общего диска нет);
- хранить результаты сборки и скачивать их после запуска.

В работе job `build` создаёт `report.txt` и сохраняет его как артефакт `report`, а job `show` скачивает его через `actions/download-artifact`.

### 6. Как заставить один job дождаться завершения другого? Зачем нужен линтер, если есть тесты?

Дождаться другого job можно ключом `needs: имя_job`. Например, `needs: build` в job `show` заставляет его стартовать только после успешного завершения `build`.

Линтер анализирует код, не запуская его, и находит потенциальные ошибки и проблемы стиля. Тест проверяет поведение только на конкретных примерах. В моей работе в PR убрала кавычки в `echo Hello, $1`: тест остался зелёным (на простом вводе `World` результат тот же), а shellcheck выдал предупреждение SC2086. Без кавычек ввод с пробелами или спецсимволами сломал бы скрипт, но тест этого не заметил. Линтер и тест дополняют друг друга.

## Наблюдения по ходу работы

- **Задание 1.** `hello.yml` запускается на каждый push. После смены приветствия на своё имя в списке два зелёных запуска.
- **Задание 2.** Текст из лабораторной для `manual.yml` в виде `run: echo "Курс: $COURSE"` GitHub отклонил как `Invalid workflow file` (ошибка YAML на строке 10): внутри обычной строки YAML двоеточие с пробелом считается разделителем «ключ: значение». Исправила, записав команды через блок `run: |`. После этого запуск кнопкой Run workflow прошёл, в логе виден курс `DevOps`, имя пользователя и секрет в виде `***`.
- **Задание 3.** В pull request `fix-hello` проверка lint стала красной (SC2086: нет кавычек вокруг `$1`), а test остался зелёным. После возврата кавычек оба job прошли, PR влит в `main`.
- **Задание 4.** Схема `build → show` зелёная, артефакт `report` скачивается, внутри текст `Сборка номер 1`. После удаления `needs: build` оба job стартовали одновременно. В моём запуске `show` всё равно завершился успешно, потому что `build` успел загрузить артефакт раньше, чем `show` дошёл до его скачивания. Это гонка (race condition): без `needs` порядок не гарантирован, и в другой раз `show` мог бы упасть с ошибкой `Artifact not found`. После возврата `needs` всё снова работает по порядку.
